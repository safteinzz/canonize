# AGENTS.md
Working brief for an AI coding agent: the invariants, gotchas and decisions needed to change this project correctly.

## What it is
- canonize (binary `canon`) manages a SOURCE folder the user owns (rules file, conventions, skills, `canonize.toml`) and wires it into each coding agent's own folders. It holds no rules itself; the crate ships only templates for `canon init`.
- Bare-first binary: bare `canon` opens the TUI; `status`, `fix`, `delete`, `add`, `remove`, `validate`, `setup`, `adopt`, `evict`, `config set`, `init`, `self` are the plain commands over the same engines. Every repair has a command, because an agent driving the CLI must never be told to reach for `rm`, `mv` or an editor.

## Module map
- What a user reads as conventions (since 0.3.0; house files before) the code still calls house: `houses.rs`, `Houses`, `config::house_files`, `Source::house`, `HouseRow`, `house_label` (which drops a `CONVENTIONS-` or `HOUSE-` prefix). The setting is `source.conventions`, read from `source.house` too, and its default is `conventions/*.md`, or `house/*.md` while a canon has a `house/` and no `conventions/`.
- `src/config.rs`: finds the source (`$CANONIZE_SOURCE`, else `dirs::config_dir()/canonize`), parses `canonize.toml` (deny_unknown_fields), merges built-in agent defaults (claude, codex, pi, opencode) with overrides, path helpers `expand` (`~/`) and `tilde` (display and import lines), `house_files`, `skill_names` (only folders with a SKILL.md, so a bucket is never a skill row or a link) and `strays` (the rest, each with the skills it holds down to three folders).
- `src/plan.rs`: `Plan::build` compares each agent with the source into `cells[row][agent]` (`State` + `Change` for fix + `Change` for remove), `foreign` (per agent, folders in a per-skill folder with no SKILL.md, not rows); agent-own skills (a real folder with a SKILL.md) become extra rows with `State::Own`, `Change::Adopt` for f and `Change::DeleteDir` for d; the delete only runs through `tui/typed.rs` (typed gate, the skill's name) and is filtered out of every bulk removal, `stale` (links in a per-skill folder that point into the source, or point at nothing at all wherever they point: both are debris `fix` deletes). `Change::run` executes one change. `State::id`/`State::why` feed `--json`; `Plan::unsettled` is every foreign/own cell (what `fix` never touches) and `Plan::own` the adoptable subset. `stale` is `(agent, Change)` so `stale_for` and `drifted` can answer for one agent; `Plan::drifted(Option<usize>)` takes the agent.
- `src/projects.rs`: walks `cfg.projects` up to depth 3 (skipping dot folders, `target`, `node_modules`, `dist`, `build`, never following links) for folders with `CLAUDE.md` or `AGENTS.md`. A project's convention imports live in its gitignored `CANON.md` (`plan::CANON_FILE`). Per convention: imported (in CANON.md), broken (in CANON.md naming a gone file: ReplaceImport; or still in CLAUDE.md/AGENTS.md: MoveImport into CANON.md) or missing (AddImport into CANON.md, only on request). `wiring` per project: CANON.md in `.gitignore` (`ignored`, via `git check-ignore`, AppendLine), and only while Claude is active (`claude_wiring`) CLAUDE.local.md in `.gitignore`, `@AGENTS.md` in CLAUDE.local.md when there is an AGENTS.md, no CLAUDE.md or `.claude/CLAUDE.md`, and no CLAUDE.local.md the user started (Claude stops reading AGENTS.md on its own once a CLAUDE.local.md exists), and `@CANON.md` in CLAUDE.local.md (`plan::LOCAL_FILE`, started with `plan::LOCAL_HEADER`, an HTML comment Claude strips); a `@CANON.md` in CLAUDE.md, where 0.2.0 wrote it, is broken and MoveImport'ed out. A CLAUDE.local.md that is a link or tracked by git is never written: one foreign wire says so, and `settleable` then keeps `fix` from moving convention imports out of CLAUDE.md or AGENTS.md, since Claude would lose them. `fix` includes wiring for every project that imports a convention, and any add brings it along. `Project::claude` is Claude's answer to loading files outside the project (`Approval`, read from `cfg.claude_state`, `~/.claude.json`, keys `hasClaudeMdExternalIncludesApproved` and `...WarningShown` under `projects` > the git repo's root, which is how Claude files it even when opened in a subfolder; `Project::claude_key`); a project not approved goes into `status`'s `needs you` block and `--json`'s `unsettled`, never into drift, because only the user can answer Claude. `Project::unread` is what a project's imported cell shows instead of `imported` in `status` and the TUI while no agent reads it: the first wire not in place by its state word (`unwired`, `broken`, `foreign`), else `unapproved`; `--json` keeps `linked` beside `wiring` and `claude`.
- `src/houses.rs`: conventions an agent reads in every project, `cells[house][agent]` (a `plan::Cell`). Per agent: an import-mode rules file gets the `@` line itself (claude), pi gets it in `<home>/CANON.md` which the extension loads (the cell is broken until the extension on disk is the one `plan::pi_extension` renders today; an older one canonize wrote, told by its `Written by \`canon\`` line, is replaced, any other is foreign), opencode gets the convention's absolute path in `instructions`, anything else is n/a. The files are the only state, as in projects: `fix` repoints a broken one (a gone file of the same name) and never adds one; `delete` takes them back. Adding is the Conventions tab, where agents are the rows above the projects, or `canon add -a`. `import_cell` skips a gone import named like a convention, so a moved convention is never read as the rules rename.
- `src/check.rs`: reports every folder in the skills folder that is not a skill (`config::strays`, no SKILL.md) for what it is, naming the skills it holds inside when it is a bucket an agent synced there; skips the rules checks when `rules` is empty or the file is not `.yaml`/`.yml` (the count is then left out of `counts`); otherwise validates the rules file (YAML parse, JSON schema via `jsonschema`, key order from the file's own `format.keys`, unknown keys) and each skill's `SKILL.md` frontmatter (`name`, `description`).
- `src/setup.rs`: first run. `detect_or_moved` (used by both the wizard and `canon setup`) falls back to `lost`, an import of a rules file that is gone whose name turns up in a folder next door. `detect` reads the default agents' instruction files for an `@path` import (or the file being a symlink) naming a rules file that exists and is not a convention; `Choice` holds the user's answers (`Pick::Existing|New|None`); `apply` writes starters for `New`, then `canonize.toml` with only non-default names (an empty value turns schema or conventions off) and links `~/.config/canonize` to the source when neither it nor `$CANONIZE_SOURCE` is set; `adopt` renames a real skill folder into the source and symlinks it back (fails across filesystems by design). Every wizard answer is also a `canon setup` flag (`--root --rules --schema --conventions --skills --projects`, `--house` still read, repeatable, `""` for none); with `--root` and nothing detected it starts from what that folder holds (`from_root`), and a named file that is not there is an error unless it is the starter's own name. `canon adopt --all [AGENT]` adopts every own skill, and `adopt` takes `-n`.
- `src/init.rs`: writes the starter files into a folder, never overwriting; `init::config_text` fills `templates/canonize.toml` (every setting written out with a comment explaining it, TOML lists included) for both `init` and setup.
- `src/cli.rs`: plain commands and their exit codes. `evict` moves a folder that is not a skill (`config::strays`) out of the canon into one agent's skills folder (`Change::Evict`, a rename, no link), refusing a skill of the canon and refusing while that folder is a link into the canon; `move` (`targets`, `plan_move`, `repoint`) moves the canon or something in it as `mv` reads it (into a folder that is there, else renamed; a rerun is told by where the first run landed) and rewrites every `@` import, link, shortcut and absolute setting that named the old path, skipping a file that is a symlink (writing through it would edit the canon) and reading a file inside what moved at its new path; the rename runs as its own step and a failure stops the command, and a move already done plans the repointing alone, so the same command finishes a half-done one and also adopts a folder moved by hand; `add` and `remove` (`place`) take one convention to the projects and agents named (`--every project|agent` for all), running the same cell `change`/`undo` the TUI's scope picker does, wiring included on an add; a target that already has it is said and skipped, an agent named that cannot read it is an error before anything runs; `config set` writes one key through `config::set_key`, which rewrites that key's own line, keeps every comment, and restores the file when the result no longer loads. `status --json` and `validate --json` print the same picture for a script (state ids `linked|unwired|broken|foreign|own|na|off|absent`, and `imported|none` under `conventions`, absolute paths, `unsettled` carrying the advice string, `exit` the code); `status --strict` also exits 1 when anything is unsettled, which takes in `foreign_elsewhere` (foreign convention and MCP cells, and a project's refused Claude wiring), listed under `needs you` rather than in the notes; `advice` says what a person can do about one cell (adopt command for own, `rules_mode = "import"` for a foreign rules file an agent links). `src/selfcmd.rs`: `self update|check`, same as the other crates.
- `src/mcp.rs`: MCP servers. `load` parses the canon's `mcp.toml` (`source.mcp`, default `mcp.toml`, `""` off; a table per server, `url` + `bearer_env` + `headers` or `command` + `args` + `env`, deny_unknown_fields) into `Server { name, spec: Spec }`; a value is `Val::Lit` or a whole `${NAME}` (`Val::Env`), anything mixing them is refused, an `env` variable must keep its own name and `url` is plain text, because that is all every agent can pass. Each agent gets the server in its own shape: Claude through `claude mcp add-json|remove -s user|local` (never by editing `~/.claude.json`, which a running Claude rewrites; a rewrite is remove then add, putting the old entry back if the add fails), codex `[mcp_servers.<name>]` via `toml_edit` (comments kept), pi `mcpServers` in `mcp.json`, opencode `mcp` in `opencode.json` with `{env:NAME}`. `Where` says where (`Claude { state, project: Option<(folder, claude_key)> }`, `Codex|Pi|Opencode(file)`); `current` reads an entry back into a `Spec` (`from_claude`, `from_codex`, `from_opencode`) so equal means `linked` (`added`), different means broken; keys canonize does not manage (`managed`) survive a rewrite. `Mcps::build` makes `cells[server][agent]` from each agent's global config and `projects[project][server]`, one `projects::Cell` over every active agent (Claude's local scope keyed by `projects::claude_key`, and `.codex/config.toml`, `.pi/mcp.json`, `opencode.json` in the project, gitignored when new via `projects::ignored`, refused when a link or tracked), reading Claude's state file once and each project's facts once (`slots`). `fix` rewrites what differs and completes a partly added project, never adds; `McpRemove` deletes a file only when nothing at all is left in it (a comment above the removed table is kept), then a project folder it leaves empty, and never touches `.gitignore`. A project below its git root (compared by real path, since git names the root by it) has no Claude part in its MCP cell, since Claude keeps one list per repo, and `Mcps::shared` lets the TUI say so; a refused project file shows only once the server is wanted there (`foreign` then, else it is no more than an agent that cannot take it); Claude's step goes last in a project batch, since it needs `claude` on PATH; `projects::in_git` lets any folder of a repo get its own `.gitignore`. A project batch starts with the server's own change, since `Change::key` of a batch is its first change's, and `AppendLine` skips a line already there. `unset` lists variables a used server needs and this environment lacks. A server with `token = true` has `Bearer::Kept(cfg.tokens/<name>)`: the token, typed in the form, lives in `~/.local/share/canonize/tokens/<name>` (`save_token`, folder 700, file 600, RFC 6750 characters only, `is_token`) and each agent reads that file per connection, so replacing it rewrites nothing: Claude a `headersHelper` printing the header (checked against 2.1.287 with a local server: it sends the file's token and rereads it on the next connection), opencode `Bearer {file:…}`, pi `!echo Bearer $(cat …)`; codex reads no file, so `for_codex` gives it `bearer_token_env_var = <NAME>_TOKEN` (`codex_var`) and `token_notes` tells `status` so.
- `src/tui/`: `mod.rs` App, keys and loop (first run with no config proposes setup at once); `render.rs` frame; `alert.rs` `Note` (alert yellow, reader cyan); `confirm.rs` gate (remove) and offers (fix, adopt, set up) carrying an `Action` and the green shell commands (`Change::command`); `wizard.rs` the six setup questions (folder, rules, schema, house, skills, projects), pre-filled from `setup::detect` with a note saying why, `tab`/Enter stepping forward and `shift-tab` back, Esc cancelling the whole wizard, ending in a summary offer that runs `setup::apply(Choice)`; `widgets.rs` house box furniture copied from easyssh, with the key words every footer and box key row is built from (`CREATE`, `DEL`, `FIND`, `GATE_KEYS`, `TYPED_KEYS`, ...) and `key_footer`; `line_edit.rs` (easyssh's, copied) the one editor every typed field goes through (setup answers, the server form, the typed gate), each field keeping its cursor as characters after it; `mcp.rs` the MCP tab's keys and offers; `server_form.rs` the tab's `c` and `e` (edit: no name field, the title names the server; the token field takes the token itself, masked, blank keeping the current one), a form whose save goes through `mcp::define` (`new` or over the server, keeping keys the form does not show), then `mcp::save_token`, then for an edit an offer to rewrite every entry that now differs (a new table in mcp.toml via `toml_edit`, comments kept, refused when the name exists or `load` would refuse the result, the refusal shown in the form's note row).

## Invariants
- canonize only ever creates or removes (a) symlinks pointing into the source root, (b) `@path` lines naming a file in the source and (c) a project's own wiring: its CANON.md, the `@AGENTS.md` and `@CANON.md` lines of a CLAUDE.local.md, and those two names in `.gitignore`, (d) the entries of the canon's MCP servers, by name, in each agent's MCP config, with the project files that hold them and their `.gitignore` lines (added, never taken back), and (e) inside the source only the canon's own `mcp.toml` (a server's table, written or taken out by `mcp::define`/`undefine`, keeping comments not the table's own) and, outside it, the kept token files under `Config::tokens`. It never deletes or overwrites a real file, never edits a link pointing outside the source, never copies anything into the source. `remove_link` refuses a non-symlink.
- The global rules import is also treated as a rename when an import of a gone file carries the rules file's name, so moving the canon folder is one `fix`.
- An import line is written as `@` + `tilde(path)`; detection compares trimmed lines exactly. An existing `@path` into the source whose file no longer exists is treated as a rename and replaced (`ReplaceImport`); one whose file exists (a convention imported globally) is the user's and left alone.
- Changes are deduplicated by target (`Change::key`), so agents sharing a folder (codex and pi on `~/.agents/skills`) get one link.
- A per-skill agent whose skills folder is a symlink into the canon is folder-mode wiring it no longer wants, so it is broken, not foreign, and one `Change::Batch` (`unfold_cell`) swaps the link for a folder of one link per skill; every skill row carries that same change, so dedup runs it once. A symlink pointing anywhere else stays foreign.
- `status` and `validate` exit 1 on drift/problems; errors go to stderr with exit 1. With `-a NAME` only that agent counts, notes and stale links included, and the projects' rows of the conventions table are neither printed nor gated on. Foreign and own cells are not drift, because they may be the user's deliberate choice; `status` ends with a `needs you` block naming each one and what to do, and `--strict` exits 1 on them.
- `config::load_from` canonicalizes the source root, so a source reached through `~/.config/canonize` is used by its real path; without this, imports and links would name the link and never match what agents already read.
- File writes go through the path (`fs::write`), so a symlinked instructions file stays a symlink.
- Unix only (`std::os::unix::fs::symlink`).

## CANON.md loaders
- Agents tab row `reads CANON.md` (only when `projects` is set): claude n/a (per project, via CLAUDE.local.md), pi `WriteFile` of `templates/pi-canonize.ts` to `~/.pi/agent/extensions/canonize.ts`, with `__AGENT_CANON__` replaced by the path of pi's own CANON.md (never overwritten by this row; only a house cell replaces an outdated one), opencode `JsonInstruction` adding `CANON.md` to `instructions` in `opencode.json` (plain JSON only; a file with comments is refused with a message), anything else n/a.

## Defaults (best known, overridable)
- claude: home `~/.claude`, rules `~/.claude/CLAUDE.md` import, skills `~/.claude/skills` per-skill.
- codex: home `~/.codex`, rules `~/.codex/AGENTS.md` link, skills `~/.agents/skills` folder.
- pi: home `~/.pi/agent`, rules `~/.pi/agent/AGENTS.md` link, skills `~/.agents/skills` folder. Stock pi does not resolve `@` imports, hence link.
- opencode: home `~/.config/opencode`, rules `~/.config/opencode/AGENTS.md` link, skills `~/.config/opencode/skills` per-skill (from opencode.ai/docs/rules and /skills).
- An agent is acted on only when its `home` exists and it is enabled.

## Keys
- Four tabs, in `tab` order (`shift-tab` goes back, both wrapping): Agents, Skills, Conventions, MCPs. Agents (list + card of `card_lines`, focus in `in_card`: Enter opens the card, Esc returns, f/d only act inside it; setup rows then a skills summary; `selected_row()` is `None` on the summary, where f/d act on all the agent's skill links), Skills (grid of `Plan::skill_rows` × agents, `srow`/`col`), Conventions (grid of conventions as columns, `pcol`, and rows `prow` over every agent then every project, `App::house_row` saying which; `every project` titles the agents on the header row and the `projects` section line is drawn but never selected, so `render_houses` maps `prow` to its display row for scrolling, and `render_grid` takes the header's height (1 here, 2 in Skills)), MCP (the conventions tab's rows over servers as columns, its own `mrow`/`mcol`/`mtop`; both draw through `render_places`, and both, like their `canon status` tables, have rows only for active agents (`App::grid_agents`), since one not installed or disabled can do nothing there; `o` never opens `~/.claude.json`). `d` on a skill the canon has also offers `delete <skill> from your canon`, a `Change::Batch` of every agent's link then `Change::DeleteDir` on the canon's folder, behind `tui/typed.rs`.
- F acts on the current tab only (there is no delete-all key; `canon delete` is the bulk one, and the last choice of `d` in the MCPs tab deletes the server under the cursor from the canon: every entry, its mcp.toml table and its kept token, a `Change::Batch` ending in `Change::McpUndefine`, behind `tui/typed.rs`) (agents: setup rows; skills: skill links and stale links; conventions: every agent's and project's imports, and the projects' wiring; MCP: every entry of a canon server); the CLI `canon fix` is the global one.
- Both tabs: `f` fix the selected cell (its `change`), `F` fix all in this tab, `d` delete the selected cell (its `undo`, red gate titled by what it deletes, `gate_title`), `d` means delete and nothing else and `D` is unbound (agents-only keys never fall through from the conventions or MCPs tab), Enter = `f` in agents and a toggle in houses; in houses `a`/`d` open `tui/scope.rs`, a picker of this cell / every convention in this row / this convention in every project (a project row) or every agent (an agent row), each carrying its changes; `c` creates and `e` edits a server in the MCPs tab (`n` is unbound); `v` validate and `E` edit canonize.toml work on every tab and are about none of them, so they are in the help panel only, never a footer or the header; `r` refresh, `tab`/`shift-tab` switch, `/` find, `?` help, `q` quit. Esc only goes back (out of the card, or dropping a committed filter) or cancels a box, and never quits; Ctrl-C is Esc under a box, in a form and in the `/` line, and quits from a view. Agents: `f` on an `own` cell adopts (`Change::Adopt`), and `F` never includes adopts. Houses: `o` opens the file the import sits in (the project's host file, or the agent's CLAUDE.md, CANON.md or opencode.json). No per-agent bulk keys: the CLI's `-a` covers that.
- Footers are `key_footer` over the key lists at the top of `render.rs`, in the fixed order `↵ <verb>`, the tab's own keys (`a add`, `o open` only when the row has a file, `F fix all`), `c create · e edit · d del`, `/ find · r refresh · q quit`, with `? help` pinned right; a key keeps its word on every tab (`F fix all`, `a add`, `↵ on/off` in the three grids). Each box kind's render function writes its own key row from `GATE_KEYS`, `TYPED_KEYS`, `PICKER_KEYS`, `FORM_KEYS` (plus `REQUIRED`) or `READER_KEYS`.
- `/` filters the rows of the current tab through `App::kept` (substring, else the characters in order): agents in Agents (not inside the card), skills in Skills, agent and project rows in Conventions and MCPs, never the columns. It is dropped on a tab change. `srow`, `prow` and `mrow` index the filtered lists (`skill_list`, `place_rows`, through `house_row_at`), so every selection goes through them, while `col` stays an index into `cfg.agents` (it is also the skills grid's column) and `requery` moves it onto a shown agent. Choices named `every …` still act on every row, filtered or not, and detail panes are sized from `all_places` so typing a filter never resizes them.
- Every box is drawn over the rows above the footer. The help is the `HELP` table in `render.rs`, one `(keys, what)` row per key under a lowercase heading, a row with no keys being a dim note; it is a reader whose body scrolls (`j/k`, `ctrl-d/u`, `g/G`) under an `esc close` row that never moves, with `vscrollbar` on the right border once it is taller than the box, so adding a row costs nothing but its line, and `render_help` clamps `help_scroll`, since only it knows the height.

## Tests
- No library target, so every test lives in a `#[cfg(test)] mod tests` beside the code, with `src/tmp.rs` (test-only) giving a self-deleting temp folder and hand-built `Config`/`Agent`/`Source` values. Nothing touches a real path, `HOME` is never set (it cannot be: `env::set_var` is unsafe in edition 2024 and `unsafe` is banned), so `setup::detect`/`lost` and the TUI are untested by design.
- 79 tests cover the engines and the promises: config parsing and paths, the plan's states and changes, `check`, the project scan and CANON.md moves, setup detection and adopt, the CLAUDE.local.md wiring and Claude's approval, and the 0.2.0 surface (`repoint`, `plan_move`, `targets`, `set_key`, the rename and evict guards).

## Audit fixes (keep these true)
- `import_cell` refuses a file that is a symlink into the canon, and `AddImport` refuses a symlink target: writing an import through the link would edit the rules file itself.
- Every file canonize appends to goes through `plan::read_text`, which is an error on a file that is not UTF-8 rather than an empty string: `read_to_string(..).unwrap_or_default()` then `write` replaced a real `CLAUDE.md` with one line. `import_cell` reports such a file foreign instead of planning an import into it.
- `names_file` decides whether a line is the rules import by the path it resolves to, canonicalized, so an absolute import or one through `~/.config/canonize` is recognised and never added beside. `RemoveImport` names the line that is actually in the file.
- The project `.gitignore` line counts as wired when `.gitignore` already lists it, because `git check-ignore` reads the index and reports a tracked `CANON.md` as not ignored, which made every `fix` append the line again. It is only taken back when that project has a `CANON.md`, so a line the user typed with no canonize wiring behind it stays.
- `Config::shortcut` carries `~/.config/canonize` from load time; nothing works it out mid-run, so `repoint` never reads the real config path from a test.
- `canon evict` takes both words as optional positionals and sorts them out itself, because clap binds the first positional to `NAME` and `canon evict --all pi` would otherwise be "a folder called pi with no agent".
- `edit_lines` drops only the lines it is told to; blank lines are the user's.
- A `RemoveImport` that empties a `CANON.md` deletes the file; a `CLAUDE.local.md` is deleted only when nothing but `LOCAL_HEADER` is left, and only one canonize started (it opens with `LOCAL_HEADER`) is canonize's to take apart: its `@AGENTS.md` goes back, and its `.gitignore` line too when nothing but canonize's lines are in it. One the user started gets `@CANON.md` and nothing else, so `delete` leaves it as they wrote it.
- `MoveImport` refuses a link as its target and writes the line before taking it out, so a failure leaves it twice rather than nowhere.
