# AGENTS.md
Working brief for an AI coding agent: the invariants, gotchas and decisions needed to change this project correctly.

## What it is
- canonize (binary `canon`) manages a SOURCE folder the user owns (rules file, house files, skills, `canonize.toml`) and wires it into each coding agent's own folders. It holds no rules itself; the crate ships only templates for `canon init`.
- Bare-first binary: bare `canon` opens the TUI; `status`, `fix`, `delete`, `validate`, `setup`, `adopt`, `evict`, `config set`, `init`, `self` are the plain commands over the same engines. Every repair has a command, because an agent driving the CLI must never be told to reach for `rm`, `mv` or an editor.

## Module map
- `src/config.rs`: finds the source (`$CANONIZE_SOURCE`, else `dirs::config_dir()/canonize`), parses `canonize.toml` (deny_unknown_fields), merges built-in agent defaults (claude, codex, pi, opencode) with overrides, path helpers `expand` (`~/`) and `tilde` (display and import lines), `house_files`, `skill_names` (only folders with a SKILL.md, so a bucket is never a skill row or a link) and `strays` (the rest, each with the skills it holds down to three folders).
- `src/plan.rs`: `Plan::build` compares each agent with the source into `cells[row][agent]` (`State` + `Change` for fix + `Change` for remove), `foreign` (per agent, folders in a per-skill folder with no SKILL.md, not rows); agent-own skills (a real folder with a SKILL.md) become extra rows with `State::Own`, `Change::Adopt` for f and `Change::DeleteDir` for d; the delete only runs through `tui/typed.rs` (typed gate, the skill's name) and is filtered out of every bulk removal, `stale` (links in a per-skill folder that point into the source, or point at nothing at all wherever they point: both are debris `fix` deletes). `Change::run` executes one change. `State::id`/`State::why` feed `--json`; `Plan::unsettled` is every foreign/own cell (what `fix` never touches) and `Plan::own` the adoptable subset. `stale` is `(agent, Change)` so `stale_for` and `drifted` can answer for one agent; `Plan::drifted(Option<usize>)` takes the agent.
- `src/projects.rs`: walks `cfg.projects` up to depth 3 (skipping dot folders, `target`, `node_modules`, `dist`, `build`, never following links) for folders with `CLAUDE.md` or `AGENTS.md`. A project's house imports live in its gitignored `CANON.md` (`plan::CANON_FILE`). Per house file: imported (in CANON.md), broken (in CANON.md naming a gone file: ReplaceImport; or still in CLAUDE.md/AGENTS.md: MoveImport into CANON.md) or missing (AddImport into CANON.md, only on request). `wiring` per project: CANON.md in `.gitignore` (`ignored`, via `git check-ignore`, AppendLine), and only while Claude is active (`claude_wiring`) CLAUDE.local.md in `.gitignore`, `@AGENTS.md` in CLAUDE.local.md when there is an AGENTS.md, no CLAUDE.md or `.claude/CLAUDE.md`, and no CLAUDE.local.md the user started (Claude stops reading AGENTS.md on its own once a CLAUDE.local.md exists), and `@CANON.md` in CLAUDE.local.md (`plan::LOCAL_FILE`, started with `plan::LOCAL_HEADER`, an HTML comment Claude strips); a `@CANON.md` in CLAUDE.md, where 0.2.0 wrote it, is broken and MoveImport'ed out. A CLAUDE.local.md that is a link or tracked by git is never written: one foreign wire says so, and `settleable` then keeps `fix` from moving house imports out of CLAUDE.md or AGENTS.md, since Claude would lose them. `fix` includes wiring for every project that imports a house file, and any add brings it along. `Project::claude` is Claude's answer to loading files outside the project (`Approval`, read from `cfg.claude_state`, `~/.claude.json`, keys `hasClaudeMdExternalIncludesApproved` and `...WarningShown` under `projects` > the git repo's root, which is how Claude files it even when opened in a subfolder; `Project::claude_key`); a project not approved goes into `status`'s `needs you` block and `--json`'s `unsettled`, never into drift, because only the user can answer Claude.
- `src/houses.rs`: house files an agent reads in every repo, `cells[house][agent]` (a `plan::Cell`). Per agent: an import-mode rules file gets the `@` line itself (claude), pi gets it in `<home>/CANON.md` which the extension loads (the cell is broken until the extension on disk is the one `plan::pi_extension` renders today; an older one canonize wrote, told by its `Written by \`canon\`` line, is replaced, any other is foreign), opencode gets the house file's absolute path in `instructions`, anything else is n/a. The files are the only state, as in projects: `fix` repoints a broken one (a gone file of the same name) and never adds one; `delete` takes them back. Adding is the Houses tab only, where agents are the rows above the projects. `import_cell` skips a gone import named like a house file, so a moved house file is never read as the rules rename.
- `src/check.rs`: reports every folder in the skills folder that is not a skill (`config::strays`, no SKILL.md) for what it is, naming the skills it holds inside when it is a bucket an agent synced there; skips the rules checks when `rules` is empty or the file is not `.yaml`/`.yml` (the count is then left out of `counts`); otherwise validates the rules file (YAML parse, JSON schema via `jsonschema`, key order from the file's own `format.keys`, unknown keys) and each skill's `SKILL.md` frontmatter (`name`, `description`).
- `src/setup.rs`: first run. `detect_or_moved` (used by both the wizard and `canon setup`) falls back to `lost`, an import of a rules file that is gone whose name turns up in a folder next door. `detect` reads the default agents' instruction files for an `@path` import (or the file being a symlink) naming a rules file that exists and is not a house file; `Choice` holds the user's answers (`Pick::Existing|New|None`); `apply` writes starters for `New`, then `canonize.toml` with only non-default names (an empty value turns schema or house files off) and links `~/.config/canonize` to the source when neither it nor `$CANONIZE_SOURCE` is set; `adopt` renames a real skill folder into the source and symlinks it back (fails across filesystems by design). Every wizard answer is also a `canon setup` flag (`--root --rules --schema --house --skills --projects`, repeatable, `""` for none); with `--root` and nothing detected it starts from what that folder holds (`from_root`), and a named file that is not there is an error unless it is the starter's own name. `canon adopt --all [AGENT]` adopts every own skill, and `adopt` takes `-n`.
- `src/init.rs`: writes the starter files into a folder, never overwriting; `init::config_text` fills `templates/canonize.toml` (every setting written out with a comment explaining it, TOML lists included) for both `init` and setup.
- `src/cli.rs`: plain commands and their exit codes. `evict` moves a folder that is not a skill (`config::strays`) out of the canon into one agent's skills folder (`Change::Evict`, a rename, no link), refusing a skill of the canon and refusing while that folder is a link into the canon; `move` (`targets`, `plan_move`, `repoint`) moves the canon or something in it and rewrites every `@` import, link, shortcut and absolute setting that named the old path, skipping a file that is a symlink (writing through it would edit the canon) and reading a file inside what moved at its new path; the rename runs as its own step and a failure stops the command, and a move already done plans the repointing alone, so the same command finishes a half-done one and also adopts a folder moved by hand; `config set` writes one key through `config::set_key`, which rewrites that key's own line, keeps every comment, and restores the file when the result no longer loads. `status --json` and `validate --json` print the same picture for a script (state ids `linked|unwired|broken|foreign|own|na|off|absent`, and `imported|none` under `houses`, absolute paths, `unsettled` carrying the advice string, `exit` the code); `status --strict` also exits 1 when anything is unsettled; `advice` says what a person can do about one cell (adopt command for own, `rules_mode = "import"` for a foreign rules file an agent links). `src/selfcmd.rs`: `self update|check`, same as the other crates.
- `src/tui/`: `mod.rs` App, keys and loop (first run with no config proposes setup at once); `render.rs` frame; `alert.rs` `Note` (alert yellow, reader cyan); `confirm.rs` gate (remove) and offers (fix, adopt, set up) carrying an `Action` and the green shell commands (`Change::command`); `wizard.rs` the six setup questions (folder, rules, schema, house, skills, projects), pre-filled from `setup::detect` with a note saying why, ending in a summary offer that runs `setup::apply(Choice)`; `widgets.rs` house box furniture copied from easyssh.

## Invariants
- canonize only ever creates or removes (a) symlinks pointing into the source root, (b) `@path` lines naming a file in the source and (c) a project's own wiring: its CANON.md, the `@AGENTS.md` and `@CANON.md` lines of a CLAUDE.local.md, and those two names in `.gitignore`. It never deletes or overwrites a real file, never edits a link pointing outside the source, never copies anything into the source. `remove_link` refuses a non-symlink.
- The global rules import is also treated as a rename when an import of a gone file carries the rules file's name, so moving the canon folder is one `fix`.
- An import line is written as `@` + `tilde(path)`; detection compares trimmed lines exactly. An existing `@path` into the source whose file no longer exists is treated as a rename and replaced (`ReplaceImport`); one whose file exists (a house file imported globally) is the user's and left alone.
- Changes are deduplicated by target (`Change::key`), so agents sharing a folder (codex and pi on `~/.agents/skills`) get one link.
- A per-skill agent whose skills folder is a symlink into the canon is folder-mode wiring it no longer wants, so it is broken, not foreign, and one `Change::Batch` (`unfold_cell`) swaps the link for a folder of one link per skill; every skill row carries that same change, so dedup runs it once. A symlink pointing anywhere else stays foreign.
- `status` and `validate` exit 1 on drift/problems; errors go to stderr with exit 1. With `-a NAME` only that agent counts, notes and stale links included, and the projects' rows of the houses table are neither printed nor gated on. Foreign and own cells are not drift, because they may be the user's deliberate choice; `status` ends with a `needs you` block naming each one and what to do, and `--strict` exits 1 on them.
- `config::load_from` canonicalizes the source root, so a source reached through `~/.config/canonize` is used by its real path; without this, imports and links would name the link and never match what agents already read.
- File writes go through the path (`fs::write`), so a symlinked instructions file stays a symlink.
- Unix only (`std::os::unix::fs::symlink`).

## CANON.md loaders
- Agents tab row `reads CANON.md` (only when `projects` is set): claude n/a (per project, via CLAUDE.local.md), pi `WriteFile` of `templates/pi-canonize.ts` to `~/.pi/agent/extensions/canonize.ts`, with `__AGENT_CANON__` replaced by the path of pi's own CANON.md (never overwritten by this row; only a house cell replaces an outdated one), opencode `JsonInstruction` adding `CANON.md` to `instructions` in `opencode.json` (plain JSON only; a file with comments is refused with a message), anything else n/a.

## Defaults (best known, overridable)
- claude: home `~/.claude`, rules `~/.claude/CLAUDE.md` import, skills `~/.claude/skills` per-skill.
- codex: home `~/.codex`, rules `~/.codex/AGENTS.md` link, skills `~/.agents/skills` folder.
- pi: home `~/.pi/agent`, rules `~/.pi/agent/AGENTS.md` link, skills `~/.agents/skills` folder. Stock pi does not resolve `@` imports, hence link.
- opencode: home `~/.config/opencode`, rules `~/.config/opencode/AGENTS.md` link, skills `~/.config/opencode/skills` per-skill (from opencode.ai/docs/rules and /skills).
- An agent is acted on only when its `home` exists and it is enabled.

## Keys
- Three tabs, in `tab` order: Agents, Skills, Houses. Agents (list + card of `card_lines`, focus in `in_card`: Enter opens the card, Esc returns, f/d only act inside it; setup rows then a skills summary; `selected_row()` is `None` on the summary, where f/d act on all the agent's skill links), Skills (grid of `Plan::skill_rows` × agents, `srow`/`col`), Houses (grid of house files as columns, `pcol`, and rows `prow` over every agent then every project, `App::house_row` saying which; section lines `every repo` and `projects` are drawn but never selected, so `render_houses` maps `prow` to its display row for scrolling). `D` in Skills deletes every skill link for every agent. `d` on a skill the canon has also offers `delete <skill> from your canon`, a `Change::Batch` of every agent's link then `Change::DeleteDir` on the canon's folder, behind `tui/typed.rs`.
- F and D act on the current tab only (agents: setup rows; skills: skill links and stale links; houses: every agent's and project's imports, and the projects' wiring); the CLI `canon fix` is the global one.
- Both tabs: `f` fix the selected cell (its `change`), `F` fix all in this tab, `d` delete the selected cell (its `undo`, red gate), `D` delete all (agents: every agent's undos; houses: every house import of every agent and project; agents-only keys never fall through from the houses tab), Enter = `f` in agents and a toggle in houses; in houses `a`/`d` open `tui/scope.rs`, a picker of this cell / every house file in this row / this house file in every project (a project row) or every agent (an agent row), each carrying its changes, `v` validate, `e` edit canonize.toml, `r` reload, `tab` switch, `?` help, `q` quit. Agents: `f` on an `own` cell adopts (`Change::Adopt`), and `F` never includes adopts. Houses: `o` opens the file the import sits in (the project's host file, or the agent's CLAUDE.md, CANON.md or opencode.json). No per-agent bulk keys: the CLI's `-a` covers that.

## Tests
- No library target, so every test lives in a `#[cfg(test)] mod tests` beside the code, with `src/tmp.rs` (test-only) giving a self-deleting temp folder and hand-built `Config`/`Agent`/`Source` values. Nothing touches a real path, `HOME` is never set (it cannot be: `env::set_var` is unsafe in edition 2024 and `unsafe` is banned), so `setup::detect`/`lost` and the TUI are untested by design.
- 63 tests cover the engines and the promises: config parsing and paths, the plan's states and changes, `check`, the project scan and CANON.md moves, setup detection and adopt, the CLAUDE.local.md wiring and Claude's approval, and the 0.2.0 surface (`repoint`, `plan_move`, `targets`, `set_key`, the rename and evict guards).

## Audit fixes (keep these true)
- `import_cell` refuses a file that is a symlink into the canon, and `AddImport` refuses a symlink target: writing an import through the link would edit the rules file itself.
- Every file canonize appends to goes through `plan::read_text`, which is an error on a file that is not UTF-8 rather than an empty string: `read_to_string(..).unwrap_or_default()` then `write` replaced a real `CLAUDE.md` with one line. `import_cell` reports such a file foreign instead of planning an import into it.
- `names_file` decides whether a line is the rules import by the path it resolves to, canonicalized, so an absolute import or one through `~/.config/canonize` is recognised and never added beside. `RemoveImport` names the line that is actually in the file.
- The project `.gitignore` line counts as wired when `.gitignore` already lists it, because `git check-ignore` reads the index and reports a tracked `CANON.md` as not ignored, which made every `fix` append the line again. It is only taken back when that project has a `CANON.md`, so a line the user typed with no canonize wiring behind it stays.
- `Config::shortcut` carries `~/.config/canonize` from load time; nothing works it out mid-run, so `repoint` never reads the real config path from a test.
- `canon evict` takes both words as optional positionals and sorts them out itself, because clap binds the first positional to `NAME` and `canon evict --all pi` would otherwise be "a folder called pi with no agent".
- `edit_lines` drops only the lines it is told to; blank lines are the user's.
- A `RemoveImport` that empties a `CANON.md` deletes the file; a `CLAUDE.local.md` is deleted only when nothing but `LOCAL_HEADER` is left, and only one canonize started (it opens with `LOCAL_HEADER`) is canonize's to take apart: its `@AGENTS.md` goes back, and its `.gitignore` line too when nothing but canonize's lines are in it. One the user started gets `@CANON.md` and nothing else, so `delete` leaves it as they wrote it.
- `MoveImport` refuses a link as its target and writes the line before taking it out, so a failure leaves it twice rather than nowhere.
- Claude loads an import outside the project (every house file) only after the user allows external imports there once; before that, and forever after a no, it skips them without a word, and an AGENTS.md read directly never even asks. Checked against Claude Code 2.1.287 with `claude -p`.
- Every house import of the same file is moved, `CLAUDE.md` and `AGENTS.md` copies alike (`Change::Batch`).
- `canon status -a NAME` exits on the drift it printed, not on other agents'.
- `canon delete` without `-a` also takes back the loaders (pi extension, opencode setting) and every project's CANON.md, `@CANON.md` line and `.gitignore` line.
- `demo/stage.sh run|shell` refuse without a stage; `ready` sets up by running `canon setup`, so the staged config is the one the tool writes.
- `config set source.rules` takes back the old rules import first, because that line is canonize's own and nothing recognises it once the setting changes.
- Every list of changes the TUI builds runs through `plan::dedup`, `remove_agents_all` and `remove_skills_all` included, not just the CLI's: agents that share a folder ask for the same link, and offering it twice made the second one fail (it showed in `skills.gif` as a red ✗ on `ln -s ~/dotfiles/canon/skills ~/.agents/skills`).
- `status` prints one note per reason per agent, not one per row, because a skills folder that is a link breaks every skill row with the same words.
- `status` ends its `needs you` block with one line for every agent in `folder` mode once `strays` is not empty, because that agent's skills folder is the canon's and everything it writes lands in the user's dotfiles; the remedy printed is `skills_mode = "per-skill"`. `--json` carries the same as `strays` and `writes_into_canon`.
- The `no canonize.toml` error names `canon setup` and `canon init`, never bare `canon`, because an agent driving the CLI cannot open the TUI.
- `canon setup` keeps `detect` and `lost` apart in its first line: a canon an agent reads today is `read by X`, one whose import is gone says which path went missing, because saying `read by` about a dead import reads as "nothing is wrong".
- `--help` explains CANON.md and lists every state word, `imported` included, because the table's vocabulary is the whole interface for a script.
- A dangling link in an agent's skills folder is stale, not foreign, and a link pointing at a real skill outside the canon is foreign, never `own`: `own` means a real folder `adopt` can move, and `adopt` refuses a link. The status line for foreign names says canonize leaves them alone without saying why, since the reason differs per entry.
