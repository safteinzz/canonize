# AGENTS.md
Brief for AI coding agent: invariants, gotchas, decisions needed to change this project correctly.

## What it is
- canonize (binary `canon`) manages SOURCE folder user owns (rules file, conventions, skills, `canonize.toml`) and wires it into each coding agent's own folders. Holds no rules itself; crate ships only templates for `canon init`.
- Bare-first binary: bare `canon` opens TUI; every subcommand is plain CLI over same engines. Every repair has a command, because agent driving CLI must never be told to reach for `rm`, `mv` or an editor.

## Module map
- What user reads as conventions code still calls house: `houses.rs`, `Houses`, `config::house_files`, `Source::house`, `HouseRow`, `house_label` (drops `CONVENTIONS-` or `HOUSE-` prefix). Setting is `source.conventions`, also read from old `source.house`; default `conventions/*.md`, or `house/*.md` while `house/` holds `.md` files and `conventions/` none.
- `src/config.rs`: source is `$CANONIZE_SOURCE`, else `dirs::config_dir()/canonize`; `canonize.toml` deny_unknown_fields; built-in agent defaults (claude, codex, pi, opencode) merged with overrides.
  - Two project lists, each entry `~` or absolute: `scopes` (folders walked for projects) and `projects` (folders user named). File with `projects` and no `scopes` is pre-0.5.0: list read as scopes with `legacy_projects` set, `status` counts it as drift, `fix` settles with `Change::RenameSetting` (`rename_key` rewrites key on its own line).
  - `Source::workspace_rules` (`source.workspaces`, file every workspace follows): unset, it is `workspaces.md` only while canon has one, so old canon never names missing file; `init` writes starter `templates/workspaces.md`, `setup` turns it on only when file is there.
- `src/plan.rs`: `Plan::build` compares each agent with source into `cells[row][agent]` (`State` + `Change` for fix + `Change` for remove).
  - Agent-own skills (real folder with SKILL.md) become extra rows with `State::Own`, `Change::Adopt` for f, `Change::DeleteDir` for d; delete runs only through `tui/typed.rs` (typed gate, skill's name), filtered out of every bulk removal.
  - `stale`: links in per-skill folder pointing into source (no such canon skill), or pointing at nothing; both debris `fix` deletes. `stale` is `(agent, Change)` so `stale_for` and `drifted` answer for one agent.
- `src/projects.rs`: walks `cfg.scopes` to depth 3 (`Walk`) for folders with any of `MARKERS`.
  - Walk skips dot folders, `target`, `node_modules`, `dist`, `build`, every workspace, canon and each agent's home; never follows links; treats folder `cfg.projects` lists as found without walking into it. Scope's own folder never a project, since CLAUDE.md at its top would swallow everything under it.
  - Every listed folder that exists is a project whatever it holds (`Project::scope` = scope it was found under, `Project::listed`); one that does not is `Projects::gone`: `needs you` line naming `canon project remove`, never drift.
  - `Projects::candidates`: every folder directly inside a scope (depth 1, never deeper, since below lie a project's own insides whatever version control it uses) that is neither project nor holds one, nor overlaps workspace, canon or agent's home; feeds Projects tab and pickers.
  - `Projects::missing_scopes`: scopes that are not folders; `needs you` line (`--json` kind `scope`) and yellow heading in Projects tab.
  - `adding` (CLI and TUI) refuses non-folder, scope itself, existing project, folder inside or holding one, or overlapping workspace, canon or agent's home; carries rename first on 0.4 file.
  - Project's convention imports live in its gitignored `CANON.md` (`plan::CANON_FILE`). Per convention: imported (in CANON.md), broken (in CANON.md naming gone file: ReplaceImport; or still in CLAUDE.md/AGENTS.md: MoveImport into CANON.md), or missing (AddImport into CANON.md, only on request).
  - `wiring` per project: CANON.md in `.gitignore` (`ignored`, via `git check-ignore`, AppendLine). Only while Claude active (`claude_wiring`): CLAUDE.local.md in `.gitignore`; `@AGENTS.md` in CLAUDE.local.md when there is AGENTS.md, no CLAUDE.md or `.claude/CLAUDE.md`, and no CLAUDE.local.md user started (Claude stops reading AGENTS.md on its own once CLAUDE.local.md exists); `@CANON.md` in CLAUDE.local.md (`plan::LOCAL_FILE`, started with `plan::LOCAL_HEADER`, HTML comment Claude strips). `@CANON.md` in CLAUDE.md (old placement) is broken and MoveImport'ed out.
  - CLAUDE.local.md that is a link or tracked by git is never written: one foreign wire says so, and `settleable` then keeps `fix` from moving convention imports out of CLAUDE.md or AGENTS.md, since Claude would lose them.
  - `fix` includes wiring for every project importing a convention; any add brings it along.
  - `Project::claude`: Claude's answer to loading files outside project (`Approval`, read from `cfg.claude_state`, `~/.claude.json`, keys `hasClaudeMdExternalIncludesApproved` and `...WarningShown` under `projects` > git repo's root, where Claude files it even when opened in subfolder; `Project::claude_key`). Unapproved project goes into `status`'s `needs you` block and `--json`'s `unsettled`, never drift, because only user can answer Claude.
  - `Project::unread`: imported cell shows, in `status` and TUI, first wire not in place by its state word (`unwired`, `broken`, `foreign`), else `unapproved`, instead of `imported` while no agent reads it. `--json` keeps `linked` beside `wiring` and `claude`.
- `src/workspaces.rs`: workspace = folder kept outside repos of projects it works on (folder per issue under it), pointed at them under `[workspaces]` in canonize.toml (`config::Workspace`).
  - Config: key and each project `~` or absolute, one path or list, read as `toml::Value` so wrong shape gets our own error. Hand-written empty list loads and is `needs you` line naming `canon link` and `canon unlink`, since refusing it would leave nothing that loads to unlink it with. Key kept as written so `unlink` takes out that line. Written by `config::set_workspace` through `toml_edit`: string for one project, inline array for more; starts table with same comment template carries, keeps comment after value, restores file when result no longer loads.
  - `link` (shared by CLI and TUI) adds projects to workspace's; refuses folder inside, or holding, a project, canon, agent's home or another workspace, because agent started in either would read the other's file. `dropping` takes projects out; last one out is `unlinking`. `Projects::build` never walks into workspace, so canonize's own CLAUDE.md there never makes it a project.
  - At its top canonize writes CLAUDE.md (claude) and AGENTS.md (every other agent), each `body`: `HEADER` (carries `MARK`, by which file is known as canonize's), `CONTEXT_FILE` (CONTEXT.md, user's notes; canonize never writes or deletes it), CANON.md, canon's workspaces.md when `workspaces::rules` on, all named whether there or not so neither appearing nor changing makes file stale; then a `Section` per project with absolute paths to read (`reads`: existing `READ` files, CLAUDE.local.md only when user started it, then `conventions` it imports or will once fixed).
  - No `@` imports, because Claude files external-imports approval per folder outside git, so every new issue folder would ask again.
  - Workspace's own conventions are `Entry::own`, `projects::workspace` read at its root (its CANON.md alone, since CLAUDE.md and AGENTS.md there are canonize's or user's, so `@` line in user's never moved or deleted); they live in its CANON.md like a project's (`canon add <CONVENTION> <WORKSPACE>`, `--every workspace`, the card). Adding one brings workspace's files along; body names CANON.md, so nothing else rewritten.
  - `Entry::via`: per convention, workspace's projects already importing it. `Reach` adds active agents that have a convention or server everywhere (global cell linked) and those that do not. Once a project brings it or every active agent has it, card shows line as `via`, Enter, `f` and `d` only say where it comes from, `canon add` skips it, so workspace never takes on what its agents already get; while only some agents have it, line keeps own state and says which do.
  - Project outside scanned folders read where it is (`projects::project`) for its conventions.
  - `Entry::cells[agent]`: missing is unwired (`WriteFile`), canonize's with another body is broken (`DeleteFile` then `WriteFile`), anything else foreign. Workspace folder not on this machine: `-`, no drift. Gone project folder (`Entry::gone`): every cell broken with no change, so `needs you` line naming `canon link` and `canon unlink <WORKSPACE> <PROJECT>`, never drift.
  - `fix` writes missing or stale, repoints workspace's own imports, keeps its CANON.md out of git (only without `-a`). `delete` takes back every file canonize wrote and its convention imports (`Entry::undos`), or with `-a` the one file that agent reads; config entries stay, so `fix` writes them again. `unlink` also takes back its MCP servers and forgets workspace only when everything before worked (`Change::after_all`, honoured by both runners), so what failed to come back stays listed.
  - In git repo, each file canonize writes at top kept out of git by anchored `/CLAUDE.md` or `/AGENTS.md` line in its `.gitignore` (`kept_out`; anchored because bare name would hide user's own files of that name in every issue folder), added with file, never taken back; missing line is `broken`.
  - `Entry::unread`: no active agent reads its CANON.md (each file missing or user's): `status` notes it beside its conventions, card shows that file's state on imported convention, `add` says so.
  - `add` and `remove` on a project, and Conventions tab's toggles and pickers, rewrite its workspaces in same run (`refresh`, with columns added and taken out, each workspace once with edits of every project it lists, since one rewrite per project would keep only first), so never stale.
  - `canon move` of canon, workspace or project rewrites `[workspaces]` line (`cli::workspace_line`, key and every project; list written over several lines left alone), workspace's CANON.md imports, and every workspace file whose paths moved (`rewrites`, conventions sorted again since rename can change order; skipped when a project is gone, as `fix` does). `repoint` matches real path of what moved too, because workspace key kept as its real path.
  - Bare `<TO>` read inside canon only for what is in it; anything else renamed beside itself, moving it into canon refused; canon itself renamed beside itself too. Path typed from `~`, `/` or `./` (`typed_path`, read from current folder, spelled out).
  - `workspaces::check_move` refuses move leaving workspace overlapping what `link` refuses. `[name] # comment` header still read as its table (`header`).
  - Claude's local entries of canon's servers filed under a folder in what moves follow it (`mcp::moved_claude`: `claude mcp remove` in old folder before rename, since `claude` finds them by folder it runs in, then added under new one; entry whose folder already gone named in a note).
  - `Entry::git` worked out once per build, since it runs git and TUI sizes its pane from every workspace every frame. Outside git repo, Codex reads AGENTS.md only in folder it starts in, and Claude keys local MCP servers by folder it starts in (server added at top reaches no session in subfolder until top is git repo; its skills in `.claude/skills` at top reach subfolder either way), so `status` and TUI say so.
  - Workspace MCP servers: `Mcps::spaces` (`spaces_shared` as `shared`), same per-folder cells as a project, kept in workspace folder; TUI's workspace card is only way to add one, as MCPs tab is for projects.
  - Per-workspace skills not built: every canon skill already linked for every agent, so link in workspace adds nothing.
- `src/houses.rs`: `cells[house][agent]` (`plan::Cell`), each agent's own way (module doc). pi cell broken until extension on disk is the one `plan::pi_extension` renders today; older one canonize wrote, told by its `Written by \`canon\`` line, replaced; any other foreign. Files are only state, as in projects: `fix` repoints broken one (gone file of same name), never adds one; `delete` takes them back. Adding: Conventions tab (agents are rows above projects) or `canon add -a`. `import_cell` skips gone import named like a convention, so moved convention never read as rules rename.
- `src/check.rs`: reports every folder in skills folder that is not a skill (`config::strays`, no SKILL.md) for what it is, naming skills it holds when it is a bucket an agent synced there; skips rules checks when `rules` empty or file not `.yaml`/`.yml` (count then left out of `counts`); key order comes from file's own `format.keys`, unknown keys refused.
- `src/setup.rs`: first run.
  - `detect_or_moved` (wizard and `canon setup`) falls back to `lost`: import of gone rules file whose name turns up in a folder next door. `detect` reads default agents' instruction files for `@path` import (or file being a symlink) naming existing rules file that is not a convention.
  - `Choice` holds answers (`Pick::Existing|New|None`). `apply` writes starters for `New`, then `canonize.toml` with only non-default names (empty value turns schema or conventions off), and links `~/.config/canonize` to source when neither it nor `$CANONIZE_SOURCE` set.
  - `adopt` renames real skill folder into source and symlinks it back (fails across filesystems by design). `canon adopt --all [AGENT]` adopts every own skill; `adopt` takes `-n`.
  - Every wizard answer also a `canon setup` flag (`--root --rules --schema --conventions --skills --scopes`; `--house` and `--projects` still read; repeatable; `""` for none). With `--root` and nothing detected, starts from what that folder holds (`from_root`); named file not there is error unless it is starter's own name.
- `src/init.rs`: writes starter files, never overwriting; `init::config_text` fills `templates/canonize.toml` (every setting written out with explaining comment) for both `init` and setup.
- `src/cli.rs`:
  - `evict` moves non-skill folder (`config::strays`) out of canon into one agent's skills folder (`Change::Evict`, rename, no link); refuses a canon skill, and refuses while that folder is a link into canon.
  - `move` (`targets`, `plan_move`, `repoint`) moves canon or something in it as `mv` reads it (into existing folder, else renamed; rerun told by where first run landed), rewrites every `@` import, link, shortcut and absolute setting naming old path, skipping file that is a symlink (writing through it would edit canon) and reading file inside what moved at its new path. Rename runs as own step, failure stops command; move already done plans repointing alone, so same command finishes half-done one and adopts folder moved by hand.
  - `add` and `remove` (`place`) take one convention to projects and agents named (`--every project|agent` for all), running same cell `change`/`undo` as TUI's scope picker, wiring included on add; target already having it is said and skipped; named agent that cannot read it is error before anything runs.
  - `project add|remove` (`project`) names folders projects or forgets them, checking every argument before anything runs; remove refuses found project not listed (only its marker file makes it one), forgets gone one by path.
  - `config set` refuses `projects` and `scopes` on 0.4 file until `fix` renames it; writes one key through `config::set_key`, which rewrites that key's own line, keeps every comment, restores file when result no longer loads.
  - `status --json` and `validate --json` print same picture for scripts (state ids `linked|unwired|broken|foreign|own|na|off|absent`, and `imported|none` under `conventions`, absolute paths, `unsettled` carrying advice string, `exit` the code). `status --strict` also exits 1 when anything unsettled, including `foreign_elsewhere` (foreign convention and MCP cells, project's refused Claude wiring), listed under `needs you`, not notes.
  - `advice` says what person can do about one cell (adopt command for own, `rules_mode = "import"` for foreign rules file an agent links).
- `src/mcp.rs`: MCP servers.
  - `load` parses canon's `mcp.toml` (`source.mcp`, default `mcp.toml`, `""` off; table per server, `url` + `bearer_env` + `headers` or `command` + `args` + `env`, deny_unknown_fields) into `Server { name, spec: Spec }`. Value is `Val::Lit` or whole `${NAME}` (`Val::Env`), mixing refused; `env` variable must keep its own name, `url` plain text, because that is all every agent can pass.
  - Each agent gets server in its own shape: Claude through `claude mcp add-json|remove -s user|local` (never editing `~/.claude.json`, which running Claude rewrites; rewrite is remove then add, putting old entry back if add fails); codex `[mcp_servers.<name>]` via `toml_edit` (comments kept); pi `mcpServers` in `mcp.json`; opencode `mcp` in `opencode.json` with `{env:NAME}`.
  - `current` reads entry back into `Spec` (`from_claude`, `from_codex`, `from_opencode`): equal is `linked` (`added`), different broken. Keys canonize does not manage (`managed`) survive rewrite.
  - `Mcps::build` makes `cells[server][agent]` from each agent's global config and `projects[project][server]`, one `projects::Cell` over every active agent (Claude's local scope keyed by `projects::claude_key`; `.codex/config.toml`, `.pi/mcp.json`, `opencode.json` in project, gitignored when new via `projects::ignored`, refused when link or tracked), reading Claude's state file once and each project's facts once (`slots`).
  - `fix` rewrites what differs and completes partly added project, never adds. `McpRemove` deletes file only when nothing at all left (comment above removed table kept), then project folder it leaves empty; never touches `.gitignore`.
  - Project below its git root (compared by real path, since git names root by it) has no Claude part in its MCP cell, since Claude keeps one list per repo; `Mcps::shared` lets TUI say so. Refused project file shows only once server wanted there (`foreign` then, else just an agent that cannot take it). Claude's step goes last in project batch, since it needs `claude` on PATH. `projects::in_git` lets any folder of a repo get own `.gitignore`.
  - Project batch starts with server's own change, since `Change::key` of batch is its first change's; `AppendLine` skips line already there. `unset` lists variables a used server needs that this environment lacks.
  - Server with `token = true` has `Bearer::Kept(cfg.tokens/<name>)`: token, typed in form, lives in `~/.local/share/canonize/tokens/<name>` (`save_token`, folder 700, file 600, RFC 6750 characters only, `is_token`); each agent rereads that file per connection, so replacing it rewrites nothing: Claude a `headersHelper` printing header, opencode `Bearer {file:…}`, pi `!echo Bearer $(cat …)`.   - `wizard.rs`: `tab`/Enter forward, `shift-tab` back, Esc cancels whole wizard; ends in summary offer running `setup::apply(Choice)`.
  - `workspaces.rs`: Workspaces tab. ## Invariants
- canonize only ever creates or removes: (a) symlinks pointing into source root; (b) `@path` lines naming file in source; (c) project's own wiring: its CANON.md, `@AGENTS.md` and `@CANON.md` lines of CLAUDE.local.md, and those two names in `.gitignore`; (d) entries of canon's MCP servers, by name, in each agent's MCP config, with project files holding them and their `.gitignore` lines (added, never taken back); (e) inside source only canon's own `mcp.toml` (server's table, written or taken out by `mcp::define`/`undefine`, keeping comments not the table's own) and, outside it, kept token files under `Config::tokens`; (f) CLAUDE.md and AGENTS.md at top of workspace, each opening with `workspaces::HEADER`, with anchored `.gitignore` lines in git repo (added, never taken back), workspace's CANON.md and MCP entries as a project's, and workspace's line under `[workspaces]` in canonize.toml; its CONTEXT.md never written; (g) in canonize.toml, `projects` list user names folders in, and one-time rename of 0.4 `projects` to `scopes`. Never deletes or overwrites real file, never edits link pointing outside source, never copies anything into source. `remove_link` refuses non-symlink.
- Global rules import also treated as rename when import of gone file carries rules file's name, so moving canon folder is one `fix`.
- Import line written as `@` + `tilde(path)`; detection compares trimmed lines exactly. Existing `@path` into source whose file is gone is a rename, replaced (`ReplaceImport`); one whose file exists (convention imported globally) is user's, left alone.
- Changes deduplicated by target (`Change::key`), so agents sharing a folder (codex and pi on `~/.agents/skills`) get one link.
- Per-skill agent whose skills folder is symlink into canon is folder-mode wiring it no longer wants: broken, not foreign; one `Change::Batch` (`unfold_cell`) swaps link for folder of one link per skill; every skill row carries same change, so dedup runs it once. Symlink pointing anywhere else stays foreign.
- `status` and `validate` exit 1 on drift/problems; errors go to stderr with exit 1; every error shown goes through `said` (main.rs), which writes OS error in OS's words without its number (`os_words`). With `-a NAME` only that agent counts, notes and stale links included; projects' rows of conventions table neither printed nor gated on. Foreign and own cells not drift, because they may be user's deliberate choice; `status` ends with `needs you` block naming each and what to do; `--strict` exits 1 on them.
- `config::load_from` canonicalizes source root, so source reached through `~/.config/canonize` used by real path; else imports and links would name the link and never match what agents already read.
- Agent not installed shown nowhere a person reads: no `status` column unless `-a` names it, no row in Agents tab, no column in Skills grid (`App::installed_agents`, which `col` is kept on and `h/l` step through). `--json` still lists every agent with `installed`, so script sees whole config.
- File writes go through path (`fs::write`), so symlinked instructions file stays symlink.
- Unix only (`std::os::unix::fs::symlink`).

## CANON.md loaders
- Agents tab row `reads CANON.md` (only when `scopes` or `projects` set, `Config::has_projects`): claude n/a (per project, via CLAUDE.local.md); pi `WriteFile` of `templates/pi-canonize.ts` to `~/.pi/agent/extensions/canonize.ts`, `__AGENT_CANON__` replaced by path of pi's own CANON.md (never overwritten by this row; only a house cell replaces outdated one); opencode `JsonInstruction` adding `CANON.md` to `instructions` in `opencode.json` (plain JSON only; file with comments refused with message); anything else n/a.

## Defaults (best known, overridable)
- In `config::defaults`: claude rules import, skills per-skill; codex and pi rules link, skills `~/.agents/skills` folder; opencode rules link, skills per-skill (opencode.ai/docs/rules and /skills). pi link because stock pi does not resolve `@` imports.
- Agent acted on only when its `home` exists and it is enabled.

## Not built yet

## Keys
- Six tabs in `tab` order (`shift-tab` back, both wrapping): Agents, Skills, Projects, Conventions, Workspaces, MCPs.
- Projects is where project added or forgotten, never Conventions, whose `c` would read as making a convention.
- Workspaces: list of workspaces (`/` filters on folder and projects) and card of selected one (Enter, Esc back), as Agents; `h/l` do nothing there.
- Agents: list + card of `card_lines`, focus in `in_card` (Enter opens card, Esc returns, f/d act only inside it); setup rows then skills summary; `selected_row()` is `None` on summary, where f/d act on all agent's skill links.
- Conventions: grid, conventions as columns (`pcol`), rows `prow` over every agent then every project (`App::house_row` says which); `every project` titles agents on header row; `projects` section line drawn but never selected, so `render_houses` maps `prow` to display row for scrolling; `render_grid` takes header height (1 here, 2 in Skills).
- MCP: conventions tab's rows over servers as columns, own `mrow`/`mcol`/`mtop`; both draw through `render_places`, and both, like their `canon status` tables, have rows only for active agents (`App::grid_agents`), since one not installed or disabled can do nothing there; `o` never opens `~/.claude.json`.
- `d` on skill the canon has also offers `delete <skill> from your canon`: `Change::Batch` of every agent's link then `Change::DeleteDir` on canon's folder, behind `tui/typed.rs`.
- F acts on current tab only (agents: setup rows; skills: skill links and stale links; conventions: every agent's and project's imports, and projects' wiring; workspaces: every workspace's files, convention imports and MCP servers; MCP: every entry of a canon server outside workspaces, `Mcps::tab_fixes`); CLI `canon fix` is the global one. No delete-all key: `canon delete` is the bulk one. Last choice of `d` in MCPs tab deletes server under cursor from canon: every entry, its mcp.toml table and kept token, `Change::Batch` ending in `Change::McpUndefine`, behind `tui/typed.rs`.

## Audit fixes (keep these true)
- `import_cell` refuses file that is symlink into canon, `AddImport` refuses symlink target: writing import through link would edit rules file itself.
- Every file canonize appends to goes through `plan::read_text`, which errors on non-UTF-8 file instead of returning empty string, since writing back an empty read replaces real `CLAUDE.md` with one line. `import_cell` reports such file foreign instead of planning import into it.
- `names_file` decides whether line is rules import by path it resolves to, canonicalized, so absolute import or one through `~/.config/canonize` recognised, never added beside. `RemoveImport` names line actually in file.
- Project `.gitignore` line counts as wired when `.gitignore` already lists it, because `git check-ignore` reads index and reports tracked `CANON.md` as not ignored, so every `fix` would append line again. Taken back only when project has `CANON.md`, so line user typed with no canonize wiring behind it stays.
- `Config::shortcut` carries `~/.config/canonize` from load time; nothing works it out mid-run, so `repoint` never reads real config path from a test.
- `canon evict` takes both words as optional positionals and sorts them itself, because clap binds first positional to `NAME`, so `canon evict --all pi` would be "a folder called pi with no agent".
- `edit_lines` drops only lines it is told to; blank lines are user's.
- `RemoveImport` emptying `CANON.md` deletes file. `CLAUDE.local.md` deleted only when nothing but `LOCAL_HEADER` left, and only one canonize started (opens with `LOCAL_HEADER`) is canonize's to take apart: its `@AGENTS.md` goes back, and its `.gitignore` line too when nothing but canonize's lines in it. One user started gets `@CANON.md` and nothing else, so `delete` leaves it as written.
- `MoveImport` refuses link as target, writes line before taking it out, so failure leaves it twice, not nowhere.
- Claude loads import outside project (every convention) only after user allows external imports there once; before that, and forever after a no, skips them silently; AGENTS.md read directly never even asks.
- Every convention import of same file moved, `CLAUDE.md` and `AGENTS.md` copies alike (`Change::Batch`).
- `canon add --every workspace` (or `project`, `agent`) with nothing to act on says `nothing to add`, exits 0; `say where` only for call naming no target at all.
- `JsonUninstruction` deletes opencode.json left holding only empty `instructions` list, since that shell is what `JsonInstruction` wrote when there was none, as `McpRemove` deletes file it leaves empty.
- `canon delete` without `-a` also takes back loaders (pi extension, opencode setting) and every project's CANON.md, `@CANON.md` line and `.gitignore` line.
- `demo/stage.sh run|shell` refuse without stage; `ready` sets up by running `canon setup`, so staged config is the one the tool writes.
- `config set source.rules` takes back old rules import first, because that line is canonize's own and nothing recognises it once setting changes.
- Every change list TUI builds runs through `plan::dedup`, `delete_server` and scope pickers included, not just CLI's: agents sharing a folder ask for same link, and offering it twice fails the second.
- `status` prints one note per reason per agent, not per row, because skills folder that is a link breaks every skill row with same words.
- `status` ends `needs you` block with one line per agent in `folder` mode once `strays` non-empty, because that agent's skills folder is canon's, so everything it writes lands in user's dotfiles; printed remedy `skills_mode = "per-skill"`. `--json` carries same as `strays` and `writes_into_canon`.
- `no canonize.toml` error names `canon setup` and `canon init`, never bare `canon`, because agent driving CLI cannot open TUI.
- `canon setup` keeps `detect` and `lost` apart in first line: canon an agent reads today is `read by X`; one whose import is gone says which path went missing, because `read by` about dead import reads as "nothing is wrong".
- `--help` explains CANON.md and lists every state word, `imported` included, because table's vocabulary is whole interface for scripts.
- Dangling link in agent's skills folder is stale, not foreign; link to real skill outside canon is foreign, never `own`: `own` means real folder `adopt` can move, and `adopt` refuses a link. Status line for foreign names says canonize leaves them alone without saying why, since reason differs per entry.
